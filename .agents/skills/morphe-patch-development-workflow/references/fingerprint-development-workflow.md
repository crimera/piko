# Obfuscation-Resilient Patch and Fingerprint Workflow

> A repeatable loop for reverse-engineering Android behavior and designing resilient Morphe patches. Generated-Dex inspection and manual runtime proof are conditional deep-validation stages, not steps to perform before handing a successful patch to the user.
>
> This guide incorporates lessons from the X-Lite download unlock, X-Lite ad filtering, premium unlock attempts, fingerprint audits, build failures, and related Pi sessions in this repository.

---

## 1. Core Rule: The Exact Tested APK Is the Truth

Use each artifact for a different purpose:

| Artifact | Purpose | What it cannot prove |
|---|---|---|
| Unobfuscated dogfood build | Understand names, architecture, event types, and intended control flow | That release bytecode has the same names, implementation, or even code path |
| Reference release decomp | Learn one real obfuscation mapping and find candidate stable anchors | That a newer target release still uses the same mapping or method |
| Exact target APK | Prove the fingerprint matches the version users will patch | That the patch mutation survives compilation unless output DEX is inspected during deep validation |
| Final patched APK | Optionally prove the generated bytecode contains the intended mutation | That the user-visible behavior works without runtime/manual testing |

A dogfood-to-release mapping is a hypothesis. A successful Kotlin build is a syntax check. Only the exact target APK, generated DEX, and runtime behavior close the loop.

## 2. The Development Loop

```text
Define exact symptom and UI surface
        ↓
Reproduce on exact unpatched target APK when available
        ↓
Trace semantics in unobfuscated build
        ↓
Map the path in exact target bytecode
        ↓
List every gate and parallel implementation
        ↓
Design stable fingerprint + prove match cardinality
        ↓
Apply smallest safe mutation
        ↓
Build MPP → patch exact APK in exclusive mode
        ↓
Applied + Saved to → immediately ask the user to test
        ↓
User reports failure or requests proof?
        ├─ no → stop; do not inspect output DEX or calculate hashes
        └─ yes → inspect DEX, install, run the focused matrix, and diagnose
```

Do not skip analysis before editing, but do stop at the successful patch handoff. Full bytecode and
runtime proof is a follow-up mode, not a reason to delay the user's test request.

## 3. Phase 0 — Define the Exact Surface and Symptom

Names such as “fullscreen player,” “bottom sheet,” and “timeline download” are often ambiguous. Before searching code, record:

- App package and exact version.
- APK/APKM/XAPK source and exact local path.
- UI architecture: legacy View, Compose, URT, X-Lite, or another subsystem.
- Screen and navigation steps.
- Exact button text.
- Exact dialog/error text.
- Expected result.
- Whether a similar action works elsewhere.

### Example

```text
Surface: New X-Lite TikTok-style vertical video player
Trigger: Fullscreen player → options → Download video
Actual: “Unlock downloadable videos with Premium”
Expected: Download starts immediately
Control: Timeline Save Video already works
```

That control result strongly suggests multiple download pipelines. Treat every UI surface as separate until bytecode proves otherwise.

## 4. Phase 1 — Establish a Red-Capable Feedback Loop

A useful loop must detect the exact failure, not merely compile.

### Preferred signals

1. **Runtime signal:** manually trigger the exact UI and observe the dialog/download.
2. **Generated-bytecode signal:** assert that the final DEX contains the intended early return or branch override.
3. **Patcher signal:** assert the fingerprint matched the expected number of methods/classes.
4. **Build signal:** ensure the patch bundle and APK build successfully.

Build success alone is not red-capable for behavior.

### Minimum evidence before editing

```text
[ ] Exact APK identified
[ ] Exact failing UI steps recorded
[ ] Failure reproduced
[ ] Candidate call path found
[ ] Unpatched target bytecode captured
```

### Collapse dependency cascades first

A patcher log can report many failed public patches when one shared dependency failed. Read nested
exceptions from the earliest failure and group later failures by their deepest repeated cause
(fingerprint class, shared patch identity, or stack frame). Fix and rerun that shared dependency
before investigating wrapper patch names independently.

For preference-backed X-Lite patches, a failure in the shared settings injection can fan out to
nearly the entire patch set. Thirteen failures do not necessarily mean thirteen broken fingerprints.

## 5. Phase 2 — Identify and Freeze the Artifacts

Never accidentally compare or install stale files.

```bash
TARGET="$HOME/Downloads/twitter_12.10.1-release.0.apk"
unzip -l "$TARGET" | rg 'classes[0-9]*\.dex'
```

Record:

```markdown
- Package: com.twitter.android
- Version: 12.10.1-release.0
- Target APK path: ...
- Patch bundle path: patches-3.8.0-dev.6.mpp
- Output path: /tmp/xlite-download-test.apk
```

After patching, confirm that the CLI printed `Applied: ...` and `Saved to ...`. Check timestamps or hashes only if a stale/ambiguous output is suspected; a timed-out signing process can leave an older APK at the expected path.

Resolve compatibility from the app family's centralized declaration (for example
`COMPATIBILITY_X_LITE`). Do not add a private target list to one patch. Duplicate lists drift and
can claim different support from the shared dependencies the patch actually uses.

## 6. Phase 3 — Use Dogfood for Semantics, Not Final Addresses

The unobfuscated build is best for answering:

- Which event fires?
- Which presenter/component handles it?
- Which dependency performs the check?
- Which branch opens the upsell?
- Which method starts the real operation?
- Are there separate legacy and new implementations?

Trace end-to-end:

```text
UI click
→ event/intent
→ event handler
→ eligibility/subscription check
→ denied branch (dialog)
→ allowed branch
→ downloader/repository/network operation
```

Do not stop at the first class containing the dialog string. A resource ID may only identify dialog construction, not the deciding branch.

---

## 7. Phase 4 — Map the Exact Target Build

Use the reference release only to generate candidates. Then search the exact target APK.

### Search order

1. Exact visible dialog text or stable analytics string.
2. Event `toString()` strings such as `VideoDownloadClicked`.
3. Preserved types/interfaces.
4. Preserved method names such as `isDownloadable` or `getVariants`.
5. Kotlin metadata, `DebugMetadata`, source filenames, and data-class `toString()` fragments.
6. Ordered bytecode around the decision branch.

### Important

DEX numbering can change after patching. A class originally in `classes13.dex` may be stripped and rewritten into `classes.dex`. Search every DEX; never assume the class remains in the same file.

## 8. Phase 5 — Enumerate All Parallel Paths and Gates

Before patching, make a path table:

| Surface | Event | Gate | Denied branch | Allowed operation |
|---|---|---|---|---|
| Timeline action sheet | `DownloadMediaRequested` | Subscription feature | Timeline upsell | File downloader |
| New X-Lite video player | `VideoDownloadClicked` | Injected premium checker | Slot-based premium upsell | X-Lite network downloader |
| Legacy immersive sheet | Legacy intent/effect | Legacy checker/downloader | Legacy upsell dialog | Legacy video downloader |

Also list gates within one path:

```text
[ ] Feature flag enables option
[ ] Media says it is downloadable
[ ] User subscription check passes
[ ] Variants list is non-null
[ ] Downloader is invoked
[ ] Storage/permission handling succeeds
```

Patching visibility does not necessarily bypass eligibility. Patching eligibility does not help if a later downloader performs a second check.

---

## 9. Phase 6 — Select the Best Hook

Prefer the smallest deep hook that controls the desired behavior.

### Hook ranking

1. **Small dedicated checker method** — ideal; override its return value.
2. **Leaf policy method** — useful if all desired paths share it; assess side effects.
3. **Specific call-site result** — precise but may need multiple call sites.
4. **Event-handler branch** — valid when no reusable checker exists.
5. **Direct reimplementation in an extension** — last resort; highest maintenance cost.

### Prefer an early return

```smali
const/4 v0, 0x1
return v0
```

This is generally safer than editing labels or redirecting complex control flow.

## 10. Phase 7 — Design a Stable Fingerprint

### Anchor hierarchy

Prefer, in roughly this order:

1. Stable framework/app type descriptors.
2. Stable method signatures and public ABI types.
3. Ordered method/field access patterns.
4. Unique semantic strings.
5. Kotlin metadata or data-class strings.
6. Literals and opcode shapes only after cross-version validation.
7. Obfuscated names only for temporary reconnaissance—never production fingerprints.

### Stable vs unstable examples

| Candidate | Stability |
|---|---|
| `Lcom/x/subscriptions/SubscriptionsFeatures;` field type | Strong if preserved across tested builds |
| `isDownloadable()Z` | Strong if preserved API contract |
| `IGET_OBJECT → INVOKE_INTERFACE → MOVE_RESULT → RETURN` | Strong when combined with signature/type anchors |
| Public ABI types such as `Composer` or `Function0` | Useful when they are part of the target method's semantic contract |
| `"VideoDownloadClicked"` | Useful semantic/class anchor |
| Morphe `"L"` parameter wildcard | Appropriate when an object parameter's exact app descriptor is obfuscated |
| `E()Z`, `F()Z`, class `i`, interface `j0` | Obfuscated and unstable |
| Short names in preserved namespaces, e.g. `kotlinx/coroutines/k0` or Compose `v2` | Still potentially obfuscated; namespace is not ABI proof |
| Kotlin null-check parameter strings such as `"title"` or `"onClick"` | Compiler artifacts; retain only if needed and cross-version verified |
| Compose compiler group-key literal | Generated implementation detail; unstable |
| “second `if-eqz`” or “last boolean field” | Fragile unless semantics are proven |

### Use an anchor budget

Fingerprint filters are mandatory conjunctions, not weighted evidence. More anchors can make a
fingerprint less resilient without making it meaningfully safer.

1. Start with stable scope/signature and the strongest semantic operation chain.
2. Measure expected cardinality on every declared target.
3. Add one discriminator only when cardinality is too broad.
4. Remove each optional discriminator in turn. If cardinality remains correct, omit it.
5. Treat every retained filter as a compatibility contract requiring exact-smali evidence.

The 12.12 settings renderer retained its signature, `"title"`, and semantic Compose call, but lost
`"onClick"`. That extra filter caused a shared dependency cascade even though it was not needed for
uniqueness.

### Use ordered filters

```kotlin
internal object PremiumCheckerFingerprint : Fingerprint(
    parameters = listOf(),
    returnType = "Z",
    filters = listOf(
        fieldAccess(
            opcode = Opcode.IGET_OBJECT,
            definingClass = "this",
            type = "Lcom/x/subscriptions/SubscriptionsFeatures;",
        ),
        methodCall(
            opcode = Opcode.INVOKE_INTERFACE,
            definingClass = "Lcom/x/subscriptions/SubscriptionsFeatures;",
            parameters = listOf(),
            returnType = "Z",
            location = MatchAfterImmediately(),
        ),
        opcode(Opcode.MOVE_RESULT, MatchAfterImmediately()),
        opcode(Opcode.RETURN, MatchAfterImmediately()),
    ),
)
```

This survives changes such as:

```text
old: checker i implements l0 → SubscriptionsFeatures.E()
new: checker j implements j0 → SubscriptionsFeatures.F()
```

The class, interface, and invoked method changed; the dependency type and delegation shape remained stable.

### Scope classes through stable dependencies

When the target method itself is broad, first identify its containing class from stable constructor or field types. For example, a presenter constructor that stores `ContextualPost` and `SubscriptionsFeatures` is more durable than the presenter's obfuscated descriptor. Then scope the method fingerprint to that class and match the semantic call chain.

For obfuscated object parameters, use Morphe's `"L"` wildcard when the exact descriptor is not part of a preserved contract. Do not replace stable public descriptors with wildcards unnecessarily.

### Compose and Kotlin anchors

- Public ABI types such as `Landroidx/compose/runtime/Composer;` and `Lkotlin/jvm/functions/Function0;` can be stable when the method's role requires them.
- A package prefix alone is insufficient. Short/internal descriptors under `androidx` or `kotlinx` may still be renamed; wildcard them unless their public ABI identity is proven.
- Compiler-generated Compose group keys/literals are implementation details and can change after unrelated source edits.
- Kotlin parameter-name strings (`"title"`, `"onClick"`) come from generated null checks and may disappear. Require one only when needed for cardinality and present in every declared target.
- Compose restart/skip branches matter during mutation; a matched renderer does not prove an insertion executes.

### Scope broad fingerprints

If a pattern can exist in multiple methods:

- Add a class fingerprint.
- Add signature constraints.
- Add more ordered calls.
- Use `matchAll()` when all implementations should be patched.
- Explicitly validate expected match count.

Do not silently accept the first global match. Do not use `matchAllOrNull()?.forEach` for required behavior: zero matches then appears successful.

### Stable model stubs and patch-time adapters

Fingerprinting answers **which app class/method to mutate**. A runtime boundary answers **which app types the extension is allowed to reference directly**. Keep those decisions separate.

Use `compileOnly` stubs for the smallest set of model classes and method signatures verified across the declared releases. The stubs are compiler contracts; they must not be packaged into the extension DEX.

A readable class is not automatically a stable model. If a used method has an obfuscated or release-specific parameter/return descriptor, do not put that descriptor in a Java/Kotlin stub. Expose a bridge with `Object`, a primitive, or another verified stable type, then resolve and inject the exact target method reference at patch time:

```text
compileOnly stable model stubs
        ↓
extension direct calls to stable ABI
        ↑
patch-time owner lookup + exact descriptor injection
```

The bridge remains a direct runtime call after patching. It is not runtime reflection and does not require the extension to know the release-specific type:

```smali
invoke-virtual {p0}, Lcom/x/models/timelines/items/UrtTimelinePost;->getReleaseValue()Lcom/x/models/StableModel;
move-result-object p0
return-object p0
```

If a release-specific enum is returned, keep it behind `Object` and compare `Enum.name()` to stable semantic values. Never name the changing enum class in the extension signature.

### Indexed resolution and matching cost

As of the Morphe Patcher used by this project:

| Situation | Resolution path | Practical cost |
|---|---|---|
| Known stable class descriptor | `mutableClassDefBy(descriptor)` → descriptor-keyed class map | Average `O(1)` class lookup |
| Fingerprint with `definingClass` | `classDefByOrNull` for the defining class, then method matching | Indexed class lookup plus local method scan |
| Fingerprint with a `classFingerprint` | Class fingerprint resolves one class, then the child scans that class's methods | Avoids a global method scan when the class anchor is stable |
| Stable strings/opcode evidence only | PatchClasses candidate indexes, then fingerprint verification | Faster than blind scanning, but candidate count may be large |
| No stable owner | Global/class-chained fingerprint search | Necessary; assert cardinality and inspect matches |

The method scan is still linear in the number of methods in the resolved class. There is no durable numeric method index to hardcode. “Method 6” is not a compatibility strategy.

Use direct descriptor lookup when the owner descriptor is stable and the used method name/signature has been verified across targets. Use fingerprints when the owner is unknown, obfuscated, or must be identified by semantic bytecode. A fingerprint scoped by a stable `definingClass` already gets the indexed class lookup; replacing it with a global scan is not an optimization.

For direct resolution, validate both cardinality and shape:

```kotlin
val owner = context.mutableClassDefBy(STABLE_OWNER_DESCRIPTOR)
val matches = owner.methods.filter { method ->
    method.name == VERIFIED_NAME && method.parameterTypes.isEmpty()
}
check(matches.size == 1) {
    "Expected one getter, found ${matches.size}: ${matches.joinToString()}"
}
val getter = matches.single()
check(getter.returnType == EXPECTED_RETURN_DESCRIPTOR) {
    "Unexpected getter shape: $getter"
}
```

### Boundary verification

Before runtime testing, inspect both artifacts:

```text
[ ] Extension dependency on model stubs is compileOnly
[ ] Stub module contains only verified stable contracts
[ ] Extension artifact contains no model stub classes
[ ] No release-specific descriptor leaks into extension signatures/constant pool
[ ] Patch-time lookup asserts owner, method shape, and cardinality
[ ] Final DEX contains the injected direct invoke and its move-result*
[ ] Final DEX contains no unresolved release-specific extension reference
[ ] Runtime path uses direct calls rather than reflection
```

A `NoClassDefFoundError`, `NoSuchMethodError`, or `VerifyError` at extension load is usually a boundary leak or an incorrect compiled descriptor—not evidence that another global fingerprint is needed. Inspect the compiled extension and final DEX before adding reflection or more filters.

#### X-Lite case study

The hide-AI-posts patch applies this split:

- Stable URT/timeline models stay in the general `compileOnly` stub module.
- Disclosure-specific stubs are absent because the disclosure-source enum descriptor changes between releases.
- Stable disclosure/post owners are resolved through the descriptor index; their local getters are validated by name, parameters, return shape, and cardinality.
- Release-specific getter references are injected into `Object`-returning bridge helpers.
- Runtime uses `Enum.name()` for the stable semantic values and never names the changing enum class.
- The obfuscated timeline-success constructor remains the one global fingerprint because no stable owner descriptor was available.

## 11. Phase 8 — Prove Match Cardinality Before Trusting the Patch

`Fingerprint.method` returns one cached match. That may be the wrong one. Required fingerprints must fail fast on both zero and unexpected extra matches.

During development, use the API-compatible equivalent of:

```kotlin
val matches = MyFingerprint.matchAll().toList()
check(matches.size == EXPECTED_MATCH_COUNT) {
    "Expected $EXPECTED_MATCH_COUNT matches, found ${matches.size}: " +
        matches.joinToString { it.originalMethod.toString() }
}

matches.forEach { match ->
    println("[DEBUG-my-patch] matched ${match.originalMethod}")
}
```

Ask:

- Expected exactly one match?
- Expected one new and one legacy implementation?
- Did the target method appear in logs?
- Did a helper, serializer, or unrelated UI method also match?

For the X-Lite video case, the broad sequence around `isDownloadable()` matched the legacy handler first. Patching the first match gave false confidence while the new X-Lite handler remained unchanged.

Remove debug logging after verification.

### Model semantic shape changes explicitly

A release can change the target contract, not merely rename it. For example, an object-valued
upsell selector can become a boolean eligibility method. Keep separate fingerprints and mutations,
then assert one combined match:

```kotlin
val objectMatches = ObjectUpsellFingerprint.matchAllOrNull().orEmpty()
val booleanMatches = BooleanUpsellFingerprint.matchAllOrNull().orEmpty()
val matches = objectMatches + booleanMatches
check(matches.size == 1) {
    "Expected one upsell target across known shapes, found ${matches.size}: " +
        matches.joinToString { it.originalMethod.toString() }
}

val match = matches.single()
if (match in objectMatches) mutateObjectResult(match) else mutateBooleanResult(match)
```

Nullable matching is safe here only because zero and ambiguity fail at the combined boundary.
Each variant still needs final-DEX and runtime proof.

## 12. Phase 9 — Implement the Smallest Mutation

### Return override

```kotlin
val matches = PremiumCheckerFingerprint.matchAll().toList()
check(matches.size == EXPECTED_MATCH_COUNT)

matches.forEach { match ->
    match.method.addInstructions(
        0,
        """
        const/4 v0, 0x1
        return v0
        """.trimIndent(),
    )
}
```

### Call-site result override

```kotlin
val result = fingerprint.instructionMatches[1]
val register = result.getInstruction<OneRegisterInstruction>().registerA
fingerprint.method.addInstruction(
    result.index + 1,
    "const/16 v$register, 0x1",
)
```

### Register rules

- `const/4` only supports `v0..v15`.
- Use `const/16` for registers such as `v24`.
- Preserve `invoke-*` followed immediately by its `move-result*`.
- Do not overwrite `p0` unless the method will return before `this` is used.
- For multiple edits, work from highest index to lowest or rematch after mutation.

### Label rules

- Prefer early returns over custom branches.
- Do not define a label in inline smali and also bind the same name with `ExternalLabel`.
- Use unique patch-prefixed label names when labels are unavoidable.

### Control-flow and representation rules

- Inspect every predecessor and branch target around the insertion point.
- An injected call can exist in final DEX yet be skipped because a loop exit, Compose skip branch, or existing label targets the original instruction after it.
- Hook the final value consumed by the UI/operation, not an intermediate builder value.
- Preserve the consumer's representation. If the original path converts an `ArrayList` to an immutable list, filter the list and convert it back before the consumer receives it.
- Preserve Compose restart-group/skip behavior unless the patch deliberately replaces the whole composable.

## 13. Phase 10 — Build and Patch the Exact APK

### Build the actual bundle

```bash
./gradlew :patches:build --no-daemon
VER=$(awk -F= '/^version/{gsub(/[[:space:]]/, "", $2); print $2}' gradle.properties)
MPP="patches/build/libs/patches-${VER}.mpp"
test -f "$MPP"
```

`compileKotlin` only proves Kotlin compilation. Build the MPP used by the CLI.

### Patch in exclusive mode first

```bash
java -jar morphe-desktop-1.11.0-all.jar patch \
  -p "$MPP" \
  --keystore Morphe.keystore \
  --exclusive \
  -e "Download patch" \
  --force \
  -o /tmp/xlite-download-test.apk \
  "$TARGET"
```

Exclusive mode reduces interaction with unrelated patches and shortens diagnosis.

After a successful isolated patch, hand the output APK to the user immediately. Do not retest the normal production patch set before asking the user to test. Run the production matrix only after a failure report or an explicit request.

### CLI cautions

- Resolve the exact MPP path; do not rely on a glob when multiple versions exist.
- Keep `-e` options associated with the intended patch command/patch bundle.
- Use an explicit output path.
- Confirm `Applied:` and `Saved to:` logs.
- A dependency shown as “disabled” in filtering logs may still execute through another patch; verify bytecode rather than interpreting logs loosely.

### Default handoff

Once the CLI reports `Applied: ...` and `Saved to ...`, immediately ask the user to test the output
APK and stop. Do not calculate hashes, extract/search output DEX, install it, run `adb` checks, or
retest the production patch set before this handoff. Those are conditional deep-validation steps.

### Required regression matrix

- New APK: run the isolated repaired patch, then every production patch that depends on the changed shared fingerprint/dependency.
- Existing APKs: repatch every declared target version affected by a removed, weakened, wildcarded, or shape-variant fingerprint.
- Compatibility: update only the centralized app-family constant after the production set applies on the new APK.
- A shared fingerprint change is not validated by one consumer passing.

## 14. Phase 11 — Optional Generated-Dex Inspection

Only do this after the user reports a failure or explicitly requests deeper validation. Never infer
mutation success from `Applied: Patch Name` when making a proof claim.

```bash
rm -rf /tmp/patched-dex
mkdir -p /tmp/patched-dex
unzip -q /tmp/xlite-download-test.apk 'classes*.dex' -d /tmp/patched-dex
```

Search every DEX for the target class. Then inspect the method with baksmali/dexlib. JADX is useful for semantics but is not the final instruction authority.

### Required proof

For a checker override, verify the actual final method begins with:

```text
const/4
return
```

Example verified output:

```text
METHOD Lcom/x/video/tab/j;->a()Z
0000 const/4
0001 return
0002 iget-object  ...SubscriptionsFeatures;
0003 invoke-interface ...->F()Z
0004 move-result
0005 return
```

The old body can remain unreachable after the early return.

For an inserted hook, instruction presence is insufficient. Inspect incoming branches and labels to prove the hook is on the executed path. Also verify that the value produced by the hook is the value returned, stored, or passed to the actual consumer with the expected runtime type.

When checking uniqueness, count actual host-app invoke sites. Raw string/reference counts can be
inflated by extension implementations, registration metadata, or `EnclosingMethod` annotations.
Print the matching owners and inspect each call site rather than trusting `rg | wc -l` alone.

### Why inspect output DEX?

It catches:

- Wrong first match.
- Mutation overwritten by another patch.
- Stale MPP.
- Stale output APK.
- Class moved to another DEX.
- Register/label compilation failures.
- A patch that logged success but changed a different method.
- A branch target that skips the injected instructions.
- A mutation applied to an intermediate value later replaced or reconverted.

## 15. Phase 12 — Install Without Destroying the Test State

Only install and run the APK when the user requests agent-side testing or after a reported failure
requires diagnosis. A successful patch is handed to the user first.

```bash
adb devices -l
adb install -r /tmp/xlite-download-test.apk
adb shell monkey -p com.twitter.android \
  -c android.intent.category.LAUNCHER 1
```

Use `-r` to preserve app data. Never uninstall unless signature incompatibility makes it necessary and the user accepts data loss.

Record which patch set was installed. An exclusive test APK may omit unrelated production patches.

## 16. Phase 13 — Manual Test Matrix

After a successful patch, ask the user to test the exact failing path first. Use this matrix for
user instructions or conditional deep validation, not as work to perform before the handoff.

### Template

| Case | Steps | Expected |
|---|---|---|
| Primary failure | New X-Lite fullscreen player → options → Download | Starts download; no premium dialog |
| Non-downloadable media | Same on protected media | Option/action behaves as intended by patch |
| Timeline control | Timeline media sheet → Save Video | Still works |
| Legacy control | Legacy immersive sheet, if enabled | No regression |
| Negative control | Disable/remove patch and repeat | Original gate returns, where practical |
| Restart | Force-stop/relaunch and repeat | Behavior persists |

When runtime testing fails, leave the failing screen open and capture:

```bash
adb logcat -c
# reproduce
adb logcat -d | rg -i 'AndroidRuntime|premium|download|morphe|piko'
```

Do not call the task complete until the user-visible symptom is gone.

## 17. Failure Triage Loop

When manual testing fails, do not immediately add another hook. Walk backward through evidence:

```text
Did the correct APK get installed?
  no → fix artifact/install process
  yes ↓
Does final DEX contain the mutation?
  no → fingerprint/mutation/build problem
  yes ↓
Did the mutated method execute?
  no → wrong code path or parallel implementation
  yes ↓
Did its result reach the deciding branch?
  no → second gate/result overwritten
  yes ↓
Did allowed branch invoke real operation?
  no → downstream eligibility or data failure
  yes ↓
Runtime/storage/network issue
```

Every failed test should eliminate one assumption.

## 18. Common Errors Found in This Repository’s Sessions

### Error 1 — Confusing UI implementations

**Symptom:** Timeline downloads worked, fullscreen still showed an upsell.

**Cause:** Legacy immersive, URT timeline, and new X-Lite video player were treated as one pipeline.

**Avoidance:** Write the path table before patching. Identify the exact event and handler for each surface.

### Error 2 — Declaring an obfuscated method stable

**Symptom:** A fingerprint using `SubscriptionsFeatures.E()` worked against one release, then failed or missed the target.

**Cause:** The containing type was preserved, but method names `E()`/`F()` were still obfuscated.

**Avoidance:** Anchor on the stable type, signature, and call shape; omit the obfuscated method name.

### Error 3 — First-match false positive

**Symptom:** Patch applied successfully, but behavior did not change.

**Cause:** A broad `isDownloadable → move-result → if-eqz` pattern matched the legacy handler before the new X-Lite handler.

**Avoidance:** Scope the fingerprint, strengthen ordered filters, print match targets, or patch all intended matches.

### Error 4 — Compile success treated as behavior verification

**Symptom:** `:patches:compileKotlin` passed, but the dialog remained.

**Cause:** Compilation does not run fingerprints or inspect generated DEX.

**Avoidance:** Build MPP, patch exact APK, inspect final bytecode, then manually test.

### Error 5 — Reference release treated as final truth

**Symptom:** Analysis correctly mapped an older release but failed on the actual test version.

**Cause:** The target changed obfuscated classes/interfaces and delegated to `F()` instead of `E()`.

**Avoidance:** Keep one target version as a holdout validation build. Never design solely against the build used for discovery.

### Error 6 — Wrong field selected by position

**Symptom:** Forcing the “last `IPUT_BOOLEAN`” changed `showNotInterestedOption`, not `showDownloadButton`.

**Cause:** Positional assumptions were not mapped to constructor semantics.

**Avoidance:** Resolve each parameter/field using constructor signature, metadata, and smali. Prefer field references or stable surrounding operations over `first`/`last`.

### Error 7 — Detection logs mistaken for applied output

**Symptom:** Logs reported ads as `REMOVED`, but ads still rendered.

**Cause:** Detection worked; reconstruction failed and a catch-all returned the original list.

**Avoidance:** Log input count, output count, returned object/type, and exceptions. Verify the transformed value reaches the field/render path.

### Error 8 — Reflection against obfuscated or absent classes

**Symptom:** A helper silently failed on `ExtensionsKt` or release-only obfuscated class `kotlinx.collections.immutable.a`.

**Cause:** Runtime reflection depended on names that differed across builds.

**Avoidance:** Prefer stable interfaces and direct bytecode operations. If reflection is unavoidable, prove class/method presence in every supported build and never silently return the original value without error telemetry.

### Error 9 — Patch-all requirement missed

**Symptom:** One checker implementation was overridden, but another path still gated the feature.

**Cause:** New and legacy implementations shared the same structural pattern; only the first match was patched.

**Avoidance:** Determine expected cardinality and use `matchAll()` when all wrappers are semantically equivalent targets.

### Error 10 — Broad leaf hook assumed to cover every caller

**Symptom:** One upsell path bypassed while another direct companion/static check remained.

**Cause:** Not every UI called the same checker abstraction.

**Avoidance:** Trace each denied branch to its actual decision method. Confirm shared-leaf claims using call sites, not architecture assumptions.

### Error 11 — Invalid high-register instruction

**Symptom:** `Invalid register: v24. Must be between v0 and v15`.

**Cause:** `const/4` was used with a high register.

**Avoidance:** Use `const/16` for `v16..v255`; check opcode encoding limits before injection.

### Error 12 — Empty/invalid inline smali

**Symptom:** `Collection is empty` or “method must have at least 1 instruction.”

**Cause:** Inline smali compilation received an invalid/empty instruction sequence after an earlier failure.

**Avoidance:** Inject the smallest known-valid instruction block and inspect the first causal error, not only the dependency wrapper exception.

### Error 13 — Label collision and double definition

**Symptom:** `There is already a label with that name.`

**Cause:** Generic labels collided, or a label was defined both in inline smali and through `ExternalLabel`.

**Avoidance:** Use unique names and one label-definition mechanism. Prefer early return to avoid labels entirely.

### Error 14 — Fragile custom matching/mutation context

**Symptom:** `classDef is null` in `InlineSmaliCompiler`.

**Cause:** A matching/mutation approach did not produce the mutable method/class context expected by the compiler.

**Avoidance:** Use named `object` fingerprints, standard filters, `Match.method`, and class-fingerprint chaining where needed. Test the patch against a real APK immediately.

### Error 15 — Nonexistent guessed strings

**Symptom:** Runtime fingerprint match failure.

**Cause:** Strings such as guessed parameter/feature names existed in dogfood assumptions but not release bytecode.

**Avoidance:** Search every declared string in release smali before committing the fingerprint.

### Error 16 — CLI option or artifact confusion

**Symptom:** Requested patches were not applied, or an older MPP/output was used.

**Cause:** Incorrect option ordering, ambiguous bundle selection, or stale output path.

**Avoidance:** Resolve one explicit MPP, use exclusive mode during diagnosis, and read the `Applied:` and `Saved to:` lines. Hash/check timestamps only when stale artifacts are suspected or an evidence record is requested.

### Error 17 — Silent patch interaction

**Symptom:** In-memory match looked correct, but final output did not contain the expected mutation.

**Cause:** Another patch can touch the same class, or output verification may accidentally inspect an older APK.

**Avoidance:** First patch exclusively, inspect final DEX, then add other patches one at a time or compare exclusive vs production outputs.

### Error 18 — Zero matches silently treated as success

**Symptom:** The patch command succeeds, but final DEX has no hook.

**Cause:** `matchAllOrNull()?.forEach` skipped mutation when the fingerprint matched nothing.

**Avoidance:** Assert exact expected cardinality and include matched methods in the failure message.

### Error 19 — Injected hook exists but is unreachable

**Symptom:** Final DEX contains the extension call, yet runtime logs/behavior show it never executes.

**Cause:** An existing loop-exit or Compose skip branch targets the original conversion instruction and jumps over code inserted before it.

**Avoidance:** Inspect predecessors and labels. Insert after the branch target/result when appropriate, then prove reachability in final DEX.

### Error 20 — Mutating an intermediate collection

**Symptom:** Filtering logs show the right items removed, but the UI still renders the original actions/items.

**Cause:** The hook modified a builder list while the consumer used a later immutable conversion or separately reconstructed value.

**Avoidance:** Trace register flow to the final consumed value. Preserve or recreate the expected immutable/runtime representation after filtering.

### Error 21 — Preference semantics inverted

**Symptom:** Enabling “Hide” makes a component visible, or disabling it hides the component.

**Cause:** A helper such as `Pref.hideBanner()` already returned an inverted “should show” value; the new branch inverted it again.

**Avoidance:** Read the helper implementation and test enabled/disabled states. Do not infer boolean semantics from the method name.

### Error 22 — Manifest presence mistaken for runtime availability

**Symptom:** Launching a manifest-declared activity throws `ActivityNotFoundException` only under X-Lite.

**Cause:** App-family metadata disabled the legacy Twitter component even though its manifest entry and class remained in the APK.

**Avoidance:** Verify runtime resolution in the active app family. Prefer an extension-owned activity explicitly enabled for every supported family.

### Error 23 — Standalone activity misses runtime theme setup

**Symptom:** A new settings activity resolves but crashes while inflating AppCompat views because theme attributes are missing.

**Cause:** The legacy host applied Twitter's selected runtime palette before inflation; the standalone activity did not.

**Avoidance:** Reproduce required theme/palette initialization before `super.onCreate()` and view inflation. Test Standard, Dim, and Lights Out where supported.

### Error 24 — Compose/compiler implementation details used as anchors

**Symptom:** A fingerprint breaks after unrelated UI recompilation or across nearby versions.

**Cause:** It depended on a Compose group-key literal or exact obfuscated app descriptor.

**Avoidance:** Use semantic calls, stable model/dependency types, public ABI types, and `"L"` for genuinely obfuscated object parameters.

### Error 25 — Dependency cascade mistaken for independent failures

**Symptom:** Most preference-backed patches fail together with repeated nested exceptions.

**Cause:** One shared settings/dependency fingerprint failed; every consumer reported a wrapper failure.

**Avoidance:** Start with the earliest failure, group by deepest repeated cause, repair the shared dependency, then rerun all consumers.

### Error 26 — Redundant compiler string made mandatory

**Symptom:** A renderer's signature and semantic calls remain stable, but matching fails after a parameter such as `onClick` becomes nullable or its null check disappears.

**Cause:** A Kotlin parameter-name string was added as an unnecessary filter. Every filter is mandatory even when intended as “supporting” evidence.

**Avoidance:** Use an anchor budget. Remove each optional filter and keep it only when required for cardinality across every target.

### Error 27 — Preserved namespace mistaken for stable type

**Symptom:** A constructor fingerprint breaks because `kotlinx/coroutines/k0` becomes `l0` or a short Compose type changes.

**Cause:** Package preservation was treated as proof that an internal/short symbol was public ABI.

**Avoidance:** Verify the actual public contract. Otherwise use `"L"` and scope through stable neighboring types, resolved owners, fields, or calls.

### Error 28 — New semantic shape forced into the old fingerprint

**Symptom:** A former object-returning selector becomes a boolean gate and the old mutation no longer applies.

**Cause:** The update changed the method contract, not merely obfuscation.

**Avoidance:** Keep explicit old/new shape fingerprints, assert one combined match, and apply a shape-specific mutation.

### Error 29 — Compatibility targets duplicated per patch

**Symptom:** One patch advertises a version that its shared dependencies omit, or misses a version supported by the rest of the app family.

**Cause:** A patch defined its own `Compatibility` and target list instead of reusing the centralized constant.

**Avoidance:** Reuse the app-family compatibility declaration. Add a version only after the dependent production matrix applies.

### Error 30 — Stable model stub leaks a release-specific signature

**Symptom:** The extension builds, but app startup or first class load throws `NoClassDefFoundError`, `NoSuchMethodError`, or `VerifyError` on a model/type that is absent or renamed in one release.

**Cause:** A readable model class was treated as stable even though one used method returned an obfuscated or release-specific type. `compileOnly` prevents duplicate classes, but it does not make an incorrect method descriptor safe.

**Avoidance:** Keep the stub minimal. Move the unstable method behind an `Object`/primitive bridge, resolve the exact target method at patch time, inject a direct invoke, and inspect the extension artifact and final DEX for leaked descriptors.

### Error 31 — Global fingerprint used where the owner is already indexed

**Symptom:** Patch application scans many classes for a method that belongs to a known stable model class.

**Cause:** A global `matchAll()`/string search was used even though the owner descriptor was stable.

**Avoidance:** Use `mutableClassDefBy` and a local method/cardinality check, or give the fingerprint a stable `definingClass`/class fingerprint. Keep global searches for genuinely unknown owners.

### Error 32 — Placeholder bridge was never replaced

**Symptom:** The patch applies and the app does not crash, but the feature remains unchanged.

**Cause:** The extension's compile-time placeholder returned before patch-time instructions were injected, or the injected call was unreachable.

**Avoidance:** Inspect final DEX for the resolved direct invoke, its `move-result*`, incoming branches, and the final consumer. A harmless placeholder is not runtime proof.

## 19. Fingerprint Review Checklist

Before accepting a fingerprint:

```text
[ ] No obfuscated class names
[ ] No obfuscated method/field names
[ ] Every literal/string exists in exact target bytecode
[ ] Every retained filter is needed for cardinality; redundant anchors were removed
[ ] Kotlin parameter-name strings are omitted unless required and verified on every target
[ ] Signature constraints are correct
[ ] Ordered filters match exact smali order
[ ] Immediate relationships use MatchAfterImmediately
[ ] Class scope is narrow enough
[ ] Obfuscated object parameters use `"L"` only where appropriate
[ ] No short/internal type is treated as stable merely because its package is preserved
[ ] No compiler-generated Compose literal is the sole anchor
[ ] Expected match count is known and asserted
[ ] Shape variants assert one combined semantic target and use shape-specific mutations
[ ] Zero matches fail loudly
[ ] All intended parallel implementations are covered
[ ] Register encoding is valid
[ ] Mutation is minimal
[ ] Consumer receives the mutated value in the expected representation
[ ] Final DEX was inspected (deep validation only)
[ ] Injected instructions are reachable from the runtime path (deep validation only)
[ ] Exact runtime path was manually tested (deep validation only)
[ ] Every dependent patch was rerun after a shared fingerprint/dependency change
[ ] Every declared target affected by a fingerprint change was repatched
[ ] Compatibility comes from the centralized app-family declaration
[ ] Stable model stubs are compileOnly and minimal
[ ] Unstable descriptors are resolved at patch time and absent from extension signatures
[ ] Extension artifact contains no model stub classes
[ ] At least one different build was used as stability validation
```

## 21. Definition of Done

### Default patch handoff

The default patching task reaches its handoff point when:

1. The intended target and match cardinality were established during development.
2. The MPP was rebuilt and the exact APK was patched in exclusive mode.
3. The CLI reported `Applied: ...` and `Saved to ...`.
4. The user was immediately asked to test the output APK.

Do not claim runtime behavior is proven from this handoff alone. Do not delay it with output-Dex
inspection, hashes, installation, or production-patch regression work.

### Full validation, only when requested or needed

For a failure report or explicit proof request, additionally require:

1. Final generated DEX contains the intended reachable mutation.
2. The mutated value reaches the real consumer with the expected representation/type.
3. The exact patched APK is installed and the original path is manually verified.
4. Related paths, dependent production patches, and affected declared versions are regression-tested.
5. Compatibility reuses the centralized app-family declaration.
6. Temporary debug logs/instrumentation are removed.
7. Documentation records stable anchors, omitted compiler artifacts/unstable names, shape variants, and tested versions. Hashes are optional and collected only when artifact identity is in doubt or an evidence record requires them.

The user's test is the next action after a successful patch—not an invitation to spend another turn
on optional bytecode verification first.
